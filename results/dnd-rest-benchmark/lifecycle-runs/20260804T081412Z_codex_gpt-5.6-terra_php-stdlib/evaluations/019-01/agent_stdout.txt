It contains small request/response and validation helpers followed by the ordered route dispatch.\n- `storage.php` owns the SQLite schema version and idempotent schema initialization shared by both entry points.\n- `game.db` is the runtime SQLite database. It is created or upgraded in place; it is state, not source code.\n\nThere are no Composer dependencies or application framework layers. The built-in PHP server directs requests to `index.php`.\n\n## State and routing\n\nEach request opens the shared `game.db` lazily through `database()`. The connection enables foreign keys and a five-second SQLite busy timeout. Relational records are stored directly for users, campaigns, compendium data, and campaign children; combat sessions are stored as JSON to preserve their whole state atomically. Write helpers use transactions and translate persistence failures to the existing JSON error responses.\n\nRoutes are deliberately matched in source order. `GET` routes are handled before the `POST` request body is parsed; non-POST requests otherwise return the standard 404 response. Dynamic route parameters are matched with regular expressions and URL-decoded. Endpoint handlers call `respond()`, which emits JSON and exits, so later handlers cannot run.\n\n`POST /v1/storage/reset` clears application tables but retains the initialized schema and schema-version metadata. This is the supported way to reset benchmark state.\n\n## API groupings\n\n- Core rules: health, dice statistics, ability checks, character ability/proficiency/derived stats, and PHB spell-slot, rest, and equipment calculations.\n- Combat: deterministic initiative ordering plus persistent combat sessions and their turn/condition state.\n- Authentication: registration and login backed by password hashes in SQLite.\n- Storage and compendium: storage status/reset plus creation and lookup for monsters and items.\n- Campaigns and DM tools: campaign, character, event, party inventory, and equipment-assignment persistence; campaign state; encounter assessment/builder, fixed loot parcels, and session recaps.\n\n## Safe extension and testing conventions\n\nPreserve the observable API contract: route paths, route precedence, JSON field names and ordering, status codes, validation messages, and SQLite reset/persistence semantics are all externally visible. Prefer new focused helpers only when they remove genuine duplication without changing validation order or response construction. Keep calculations deterministic; in particular, initiative ties are ordered by score, Dexterity, then name.\n\nWhen extending storage, update `initializeSchema()` rather than duplicating DDL in a launcher. Keep related writes transactional and retain the current error mapping. Test from a clean database using the reset endpoint, then exercise both success and invalid-input paths with `curl`; run PHP lint before handoff.
