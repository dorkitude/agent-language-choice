# CODEBASE.md

A minimal Rails 8.1.3 API app that implements a D&D 5e REST toolkit: dice
and character math, stateful combat sessions, auth, a monster/item
compendium, campaign roster/quest/NPC/inventory/session/audit tracking,
PHB rules calculators, DM tools, and a live GM/player campaign-play surface
(`/v1/play`). Ruby 4.0.5.

## Starting and verifying the server

```bash
bundle install            # first run only; installs into ./vendor/bundle
PORT=8080 ./run.sh         # starts Puma in the foreground on 127.0.0.1:$PORT
```

`run.sh` runs `bundle exec rackup -o 127.0.0.1 -p "$PORT"`, which loads
`config.ru`, which requires `app.rb` and serves `Rails.application`.

Verify it's up:

```bash
curl http://127.0.0.1:8080/health   # => {"ok":true}
```

State persists in `game.db` (SQLite, WAL mode) in the project root. Delete
it (and its `-shm`/`-wal` siblings) to start from a clean database, or call
`POST /v1/storage/reset`.

## Entry point and major files

This app is **not** generated by `rails new` — there is no
`config/environment.rb`, `bin/rails`, or Zeitwerk autoloading. Instead,
`app.rb` is a single script that defines the `Rails::Application` subclass,
then `require_relative`s every other file in explicit dependency order,
then calls `DndApp.initialize!` and loads the routes. This keeps startup
deterministic and avoids autoload-path configuration for a codebase this
size.

```
app.rb                          # boots Rails::Application, wires everything together
config.ru                       # rackup entry point: require app.rb, run Rails.application
config/routes.rb                # route table, grouped by domain controller
lib/
  game_data.rb                  # static 5e reference tables (CR->XP, XP thresholds) + multiplier_for
  game_storage.rb               # GameStorage: SQLite connection, schema, reset
  persistent_collections.rb     # PersistentXxx write-through caches (see below)
  password_hasher.rb            # PasswordHasher: bcrypt hash/verify
app/controllers/
  application_controller.rb     # shared validation/auth/5e-math helpers; no routes point here
  core_controller.rb            # health, dice, ability checks, adjusted XP, initiative order
  characters_controller.rb      # ability modifier, proficiency bonus, derived stats
  combat_controller.rb          # combat session create/condition/advance-turn
  auth_controller.rb            # register/login
  storage_controller.rb         # storage status/reset
  compendium_controller.rb      # monsters/items create+read
  campaigns_controller.rb       # campaign create, roster, event log, state
  quests_controller.rb          # quest creation, progress, summary
  phb_controller.rb             # spell slots, long rest, equipment load
  dm_controller.rb              # encounter builder, loot parcel, session recap
  npcs_controller.rb            # factions, NPCs, relationship summary
  inventory_controller.rb       # campaign inventory + equipment assignment
  downtime_controller.rb        # downtime crafting projects
  sessions_controller.rb        # session scheduling + attendance
  audit_controller.rb           # audit log + campaign export
  analytics_controller.rb       # readiness summary + risk report
  play_controller.rb            # live GM/player campaign-play surface (/v1/play)
```

## State, persistence, and request routing

**Persistence model.** Every piece of mutable game state (users, combat
sessions, compendium monsters/items, campaigns, play-campaigns) lives in
one SQLite file, `game.db`, as a table of `(primary key, data JSON)` rows —
see `GameStorage.create_schema` in `lib/game_storage.rb`. On top of each
table sits a `PersistentXxx` class (`lib/persistent_collections.rb`) that
acts like a `Hash`: it loads the whole table into an in-memory `@cache`
once at boot, and every write (`[]=`, or `persist(id)` after mutating a
cached value in place) updates both the cache and SQLite synchronously.
Request handlers never talk to SQLite directly — they only touch the six
global collection objects created in `app.rb`:

```ruby
GameStorage.connect
COMBAT_SESSIONS = PersistentCombatSessions.new
USERS            = PersistentUsers.new
MONSTERS         = PersistentCompendium.new('monsters')
ITEMS            = PersistentCompendium.new('items')
CAMPAIGNS        = PersistentCampaigns.new
PLAY_CAMPAIGNS   = PersistentPlayCampaigns.new
```

Most of these (`COMBAT_SESSIONS`, `MONSTERS`, `ITEMS`, `CAMPAIGNS`,
`PLAY_CAMPAIGNS`) are `PersistentJsonTable` subclasses sharing one
`(id, data TEXT)` table shape, where `data` is a JSON-serialized hash;
`PersistentUsers` is separate because its table has typed, non-JSON
columns (`username`, `role`, `password_digest`). `PersistentCombatSessions`
overrides `load_cache` because its nested hashes need symbol keys rebuilt
explicitly on load rather than a flat symbolized JSON parse.

Domain state that doesn't warrant its own table (quests, NPCs, factions,
inventory, crafting projects, scheduled sessions, campaign-play members and
event log) is stored inline inside the owning `CAMPAIGNS`/`PLAY_CAMPAIGNS`
hash under a dedicated key (e.g. `campaign[:quests]`, `play_campaign[:members]`)
and written back with `.persist(id)` after each in-place mutation.

Because reads are served from memory, this design assumes a single
process/worker — it is not safe to run multiple Puma workers against the
same `game.db` cache.

**Request routing.** `config/routes.rb` maps each REST path to
`controller#action`, e.g. `post '/v1/combat/sessions', to:
'combat#create_combat_session'` dispatches to
`CombatController#create_combat_session`. Controllers are grouped by
domain (see below), all inheriting from `ApplicationController`, which
itself holds no actions — only cross-cutting helpers (`valid_integer?`,
`ability_mod`, `proficiency_bonus`, `encounter_thresholds`,
`difficulty_for`, `compare_by_score_dex_name`, `authenticate_user!`,
`authenticate_play_actor!`) used by more than one controller. Every action
follows the same shape: validate `params` in order, `render json: {
error: '...' }, status: :bad_request` (or `:not_found` / `:conflict` /
`:unauthorized` / `:forbidden`) and `return` on the first failure,
otherwise `render json: { ... }` with the success body.

`PlayController` (the `/v1/play` surface) additionally layers
authorization on top of authentication: every action calls
`authenticate_play_actor!` first, then `load_campaign_or_404`, then one of
`require_owner!` / `require_participant!` to render 403 for a
valid-but-unauthorized actor, before validating params and applying the
state change. These `require_*!` helpers, plus the `load_encounter_or_404`
and `load_character_member_or_404` lookups and the `require_character_owner!`
ownership check used across the encounter and character-progression actions,
all render the error response and return falsy/nil on failure so callers can
`return unless ...`.

## API/domain groupings

| Controller | Routes | Purpose |
|---|---|---|
| `CoreController` | `GET /health`, `POST /v1/dice/stats`, `/v1/checks/ability`, `/v1/encounters/adjusted-xp`, `/v1/initiative/order` | Health check + stateless dice/XP/ordering math |
| `CharactersController` | `POST /v1/characters/ability-modifier`, `/proficiency`, `/derived-stats` | Character sheet math (ability mod, proficiency bonus, HP/AC) |
| `CombatController` | `POST /v1/combat/sessions[...]` | Stateful initiative/condition/turn tracking, backed by `COMBAT_SESSIONS` |
| `AuthController` | `POST /v1/auth/register`, `/login` | User accounts, backed by `USERS`; bcrypt via `PasswordHasher` |
| `StorageController` | `GET /v1/storage/status`, `POST /v1/storage/reset` | Introspect/wipe the SQLite-backed state |
| `CompendiumController` | `POST`/`GET /v1/compendium/monsters`, `/items` | Shared monster/item reference data, backed by `MONSTERS`/`ITEMS` |
| `CampaignsController` | `POST /v1/campaigns[...]`, `GET /v1/campaigns/:id/state` | Campaign roster, event log, and state readback, backed by `CAMPAIGNS` |
| `QuestsController` | `POST /v1/campaigns/:id/quests[...]`, `GET .../quests/summary` | Quest creation, milestone progress, summary counts |
| `PhbController` | `POST /v1/phb/spell-slots`, `/rests/long`, `/equipment-load` | Player's Handbook rules calculators |
| `DmController` | `POST /v1/dm/encounter-builder`, `/loot-parcel`, `/session-recap` | DM tools built on top of `MONSTERS`/`CAMPAIGNS` |
| `NpcsController` | `POST /v1/campaigns/:id/factions`, `/npcs`, `GET .../relationships` | Factions, NPCs, relationship summary |
| `InventoryController` | `POST /v1/campaigns/:id/inventory`, `.../characters/:cid/equipment`, `GET .../inventory/summary` | Campaign inventory and equipment assignment |
| `DowntimeController` | `POST /v1/campaigns/:id/downtime/crafting[...]` | Downtime crafting project creation and progress |
| `SessionsController` | `POST /v1/campaigns/:id/sessions[...]`, `GET .../sessions/next` | Session scheduling and attendance |
| `AuditController` | `GET /v1/campaigns/:id/audit`, `/export` | Read-only audit log and export summary |
| `AnalyticsController` | `GET /v1/campaigns/:id/analytics/summary`, `POST .../risk-report` | Deterministic readiness summary and risk report |
| `PlayController` | `POST /v1/play/campaigns[...]`, `GET`/`PUT .../turn`, `/my-turn`, `/gm/status`, `/document`, `/scenes[...]`, `/locations[...]`, `/encounters[...]`, `/characters/:char_id[...]` | Live GM/player campaign-play: lobby, exploration turn order (narration/action/resolution/nudge/travel/rest), scenes, the location graph, campaign-bound encounters (combatants, initiative, damage/healing/conditions, rewards), and per-character state (HP/death saves/ownership/build/level-up/skill checks) |

Static rules tables (`CR_XP`, `LEVEL_THRESHOLDS` in `lib/game_data.rb`;
`WIZARD_SPELL_SLOTS` in `PhbController`; `LOOT_TIERS`,
`RECOMMENDATIONS` in `DmController`; `VALID_STANCES` in `NpcsController`;
`VALID_STATUSES` in `QuestsController`) are intentionally scoped to only
the values this benchmark's evaluator suites exercise — extend them rather
than assuming full 5e coverage.

## Conventions for extending and testing

- **Adding an endpoint:** add the action to the right domain controller
  (or a new one, subclassing `ApplicationController`), then add its route
  in `config/routes.rb`. If it's a new file, `require_relative` it from
  `app.rb` in the same section as its siblings (there is no autoloading).
- **Validation style:** validate every param up front with `unless
  valid?(...) ; render ... ; return ; end` guards (or the `require_*!`
  early-return helpers used by `PlayController`), in the same order the
  evaluator suite checks them — response `error` strings and HTTP status
  codes are part of the contract tests assert against.
- **New persisted state:** prefer storing it inline on the existing
  `CAMPAIGNS`/`PLAY_CAMPAIGNS` hash (under a new key, persisted via
  `.persist(id)`) if it's campaign-scoped. Only add a whole new SQLite
  table (in `GameStorage.create_schema` and `GameStorage.reset`) plus a new
  `PersistentJsonTable` subclass in `lib/persistent_collections.rb` for
  state that isn't naturally owned by one campaign row; instantiate it as
  a global constant in `app.rb` alongside `COMBAT_SESSIONS` etc.
- **Testing:** there is no in-repo test suite; correctness is verified by
  running the external evaluator against a live server:
  ```bash
  PORT=8080 ./run.sh &
  dndeval run --suite 030-campaign-document --base-url http://127.0.0.1:8080
  ```
  The evaluator suites are cumulative (each later suite is a superset of
  the earlier ones), so run the latest suite ID relevant to your change to
  confirm nothing regressed.
